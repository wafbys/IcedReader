# 想法：EPUB 稳定标识（待定，勿实现）

状态：**模糊需求，记录待后续想清楚**。不要据此动手，也不要并入 AGENTS 硬约束。

## 背景

- 同一本书常有多份 epub（不同站点 / 工具反复重打包），文件名、`dc:identifier`、封面、字体、哈希都会变。
- 用户想用「组合方式」尽可能探测一本 epub 的**稳定标识**，用于（候选用途）识别重复、重打包后保留进度/划线。
- `scripts/epub-id.py` 是早期实验（dc:identifier → 全内容哈希 → size+mtime），问题已知，尚未定方案。

## 待定问题（想清楚再设计）

1. 主要用途：书库去重合并条目 / 重打包后保留进度划线 / 仅外部查重工具？
2. 「同一本」容忍度：不同排版、不同封面、修订版是否算同一本；合并错误可否接受自动做，还是列候选人工确认？
3. 成本门槛：首次入库算正文指纹（大书 1–3 s，缓存于 data/）是否可接受。
4. 方案倾向（讨论过、未定稿）：
   - 输出「候选 id 集合 + 来源/置信度」，而非单一哈希。
   - `dc:identifier` 按形态分级（isbn/url 可信；`urn:uuid` 多为每次重打生成，不可信）。
   - 内容哈希排除面需含封面、字体、版权页等重打包最爱动的文件。
   - 更稳的信号是「按 spine 顺序的正文文本指纹（去空白、含章数）」。
   - 若做「重打包保留进度」：不宜把指纹当主键（大书扫描成本 + 老记录迁移），倾向做**识别别名层**：入库时算指纹并缓存，发现命中旧书再决定合并。
   - 计算放 Rust（zip/rbook 已有），python 脚本仅作开发期对照。
5. 若定稿会动书架去重/进度语义，需同步 AGENTS（现「不做内容哈希去重，除非产品明确要求」）。
